# 06 — Category Naming Research

**Status:** Candidate Category Research  
**Scope:** Category Formation / Language Research  
**Runtime Authority:** None  
**Product Claim:** None  
**Public Claim Status:** Not approved for external use

## 1. Purpose

This document evaluates candidate names for the research thesis currently described as State Reconstruction Tax and Verified Execution State Infrastructure.

A category name must be understandable outside DETERMA. It must survive technical, buyer, developer, and analyst interpretation.

## 2. Naming Criteria

A viable category name should be:

- specific enough to be defensible
- broad enough to support a market
- distinct from memory, RAG, workflow, and authorization
- understandable to technical buyers
- compatible with academic language
- compatible with enterprise security language
- not misleading about production readiness
- not implying that DETERMA owns all enterprise reality

## 3. Rejected or High-Risk Names

### Reality Layer

Risk: too broad, too metaphysical, and difficult to defend.

It suggests ownership of all operational truth, which DETERMA does not claim.

### AI Memory

Risk: crowded category and semantically inaccurate.

Memory answers what the agent knows. The candidate thesis concerns what is operationally true and executable now.

### Authorization Engine

Risk: too narrow and already established.

The thesis includes authority but also environment, risk, provenance, freshness, execution history, and invalidation.

### AI Governance Platform

Risk: too vague and crowded.

It does not isolate the technical abstraction under investigation.

### Authority Compression

Risk: useful internally, but may sound like weakening policy or hiding important detail.

Should remain a research mechanism, not the category name.

## 4. Candidate Names

### Verified Execution State Infrastructure

Strengths:

- technically precise
- emphasizes verification
- execution-oriented
- distinct from memory
- compatible with DETERMA's runtime-authority direction

Weaknesses:

- long
- may sound like an architecture pattern rather than a market category

### Agent Execution State Control Plane

Strengths:

- familiar enterprise infrastructure language
- communicates operational control
- connects to cloud/control-plane mental models

Weaknesses:

- may imply broad orchestration ownership
- may overlap with workflow and agent-management platforms

### State Reconstruction Infrastructure

Strengths:

- directly names the problem
- category could center around State Reconstruction Tax
- broader than authority alone

Weaknesses:

- less intuitive to buyers
- may require heavy education

### Verified State Compiler

Strengths:

- strong systems analogy
- suggests transformation from raw operational sources into executable state
- developer-friendly

Weaknesses:

- may be too technical for enterprise buyers
- compiler analogy may overpromise determinism

### Execution State Layer

Strengths:

- short
- clear
- infrastructure-like

Weaknesses:

- may be too generic
- lacks verification and freshness emphasis

## 5. Recommended Working Hierarchy

Use different terms for different audiences:

### Research / Academic

**State Reconstruction Tax**

Use this to define the problem and measurement target.

### Technical Architecture

**Verified Execution State Infrastructure**

Use this for the system layer under investigation.

### Developer Primitive

**Verified State Object**

Use this for the concrete object consumed by agents or runtimes.

### Product / Category Candidate

**Agent Execution State Control Plane**

Use this only after validation, if buyer language confirms that control-plane framing is clearer.

## 6. Recommended Current Usage

Until validation exists, internal documents should use:

> State Reconstruction Tax — the problem.

> Verified Execution State Infrastructure — the candidate solution layer.

Avoid external category claims until benchmark evidence and prior-art review support the distinction.

## 7. Language Tests

The category name should be tested against these questions:

1. Can a CTO understand it in under 30 seconds?
2. Can an AI infrastructure engineer map it to an architecture?
3. Can a CISO understand why it differs from authorization?
4. Can a product leader explain why it differs from memory?
5. Can an analyst distinguish it from governance?
6. Can an academic reviewer evaluate it as a systems problem?

## 8. Naming Decision Rule

Do not select a final category name until:

- prior-art analysis is complete
- benchmark design is implemented
- at least one empirical measurement exists
- buyer-facing language has been tested
- the distinction from memory and authorization is defensible

## 9. Governance Note

This document is naming research only. It does not approve any term for public messaging.
