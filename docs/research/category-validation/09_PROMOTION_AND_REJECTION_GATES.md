# 09 — Promotion and Rejection Gates

**Status:** Candidate Governance Framework  
**Scope:** Research Governance / Category Validation / Decision Control  
**Runtime Authority:** None  
**Product Claim:** None  
**Public Claim Status:** Not approved for external use

## 1. Purpose

This document defines decision gates for advancing, weakening, or rejecting the State Reconstruction Tax and Verified Execution State Infrastructure theses.

The purpose is to prevent research artifacts from becoming product claims, canonical architecture, or public positioning before sufficient evidence exists.

## 2. Current Status

The thesis is currently classified as:

> Candidate Research Thesis

It is not:

- canonical product truth
- runtime architecture
- public positioning
- benchmarked performance claim
- category proof

## 3. Promotion Levels

### Level 0 — Draft Research Hypothesis

A speculative idea has been documented.

Allowed:

- internal discussion
- exploratory writing
- initial architecture sketches

Not allowed:

- public claims
- product roadmap commitments
- customer-facing promises

### Level 1 — Candidate Research Thesis

The problem, definitions, competing hypotheses, falsification criteria, and benchmark design exist.

Allowed:

- internal research planning
- controlled prototype design
- prior-art review
- benchmark implementation planning

Not allowed:

- claims of measured token savings
- claims of new category creation
- claims of production readiness

### Level 2 — Validated Research Finding

At least one credible benchmark or prototype produces measured evidence.

Requirements:

- reproducible benchmark cases
- baseline comparisons
- token/tool/latency attribution
- safety and correctness evaluation
- documented negative cases

Allowed:

- internal strategy update
- candidate product implication analysis
- stronger investor-facing hypothesis with caveats

Not allowed:

- general public benchmark claims without review
- broad superiority claims

### Level 3 — Candidate Canonical Strategic Thesis

The research survives prior art, benchmark evidence, and internal review.

Requirements:

- completed prior-art review
- benchmark results across multiple workloads
- no safety regression
- validated distinction from memory, workflow, authorization, and agent frameworks
- clear naming rationale

Allowed:

- promotion into canonical strategy docs
- controlled external language
- analyst-research preparation

Not allowed:

- production capability claim unless implemented

### Level 4 — Product Architecture Candidate

The thesis has a prototype or reference implementation path.

Requirements:

- technical design review
- security review
- runtime boundary review
- invalidation model review
- failure-mode analysis

Allowed:

- product discovery
- prototype implementation
- design partner exploration

Not allowed:

- production SLA claims
- customer deployment claims without deployment evidence

### Level 5 — Canonical Product Capability

The capability exists, is tested, and is documented.

Requirements:

- implementation
- tests
- security validation
- audit validation
- deployment evidence
- explicit maintainer promotion

Allowed:

- product documentation
- controlled sales enablement
- external messaging subject to approval

## 4. Rejection Paths

The thesis should be downgraded or rejected if evidence shows one of the following:

### Rejection A — Existing Category Absorption

Memory, workflow, authorization, MCP/tool protocols, or agent frameworks already solve the problem sufficiently.

Outcome:

> Treat as product feature or integration requirement, not category.

### Rejection B — Cost Immateriality

State reconstruction is measurable but not economically material.

Outcome:

> Treat as optimization detail, not strategic thesis.

### Rejection C — Unsafe Compression

Verified state objects hide material policy detail or increase false allow rates.

Outcome:

> Reject or redesign.

### Rejection D — Excessive Complexity

Invalidation, provenance, or integration complexity outweighs benefits.

Outcome:

> Treat as narrow enterprise feature, not general infrastructure.

### Rejection E — Buyer Confusion

The market cannot distinguish the thesis from memory, governance, authorization, or workflow.

Outcome:

> Reframe language or abandon category creation.

## 5. Mandatory Evidence Before External Claims

No external claim may be made unless the following exist:

- source-cited prior-art review
- reproducible benchmark design
- measured results
- baseline comparison
- safety analysis
- failure analysis
- approved messaging language

## 6. Red-Line Claims

The following claims are prohibited until explicitly validated:

- DETERMA saves more tokens than memory infrastructure
- DETERMA has created a new category
- Verified Execution State is production-ready
- Verified State Objects eliminate the need for authorization systems
- Verified State Objects eliminate the need for memory
- DETERMA owns the reality layer
- token reduction has been measured
- enterprise deployment exists

## 7. Decision Table

| Evidence State | Decision |
|---|---|
| idea only | remain Level 0 |
| definitions and falsification plan | Level 1 |
| one benchmark with weak baseline | remain Level 1 |
| one benchmark with strong baselines and no safety regression | Level 2 candidate |
| multiple workloads and prior-art survival | Level 3 candidate |
| prototype architecture reviewed | Level 4 candidate |
| implemented, tested, deployed | Level 5 candidate |

This document is a guardrail. It is designed to slow down premature promotion and preserve trust in DETERMA's canonical knowledge base.
